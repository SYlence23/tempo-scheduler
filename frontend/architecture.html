Як працює Tempo

Оптимізація розкладу з залежностями та обмеженими ресурсами. Обчислення відокремлені від HTTP-серверів, а черга повністю зберігається в PostgreSQL.

Мови компонентів

Фронтенд: HTML, CSS, JavaScript. API: JavaScript, Node.js та Express. Балансер, воркери, оптимізатор, Autoscaler і Supervisor: Python. База та черга: PostgreSQL.

Взаємозв’язки компонентів

  1. Браузер → Python-балансер. Єдина адреса застосунку. Інтерфейс надсилає параметри розкладу й отримує прогрес через SSE.
  2. Python-балансер → API_1 / API_2. least_conn обирає API з меншою кількістю активних з’єднань. Заголовок X-Served-By показує, хто відповів.
  3. API → PostgreSQL. Перевірка JWT, валідація DAG, лімітів і прав власника; збереження нової задачі зі статусом queued. Блокування рядка користувача робить перевірку ліміту активних задач атомарною.
  4. Воркери → PostgreSQL. Кожен воркер атомарно захоплює вільний рядок. SKIP LOCKED пропускає рядки, які вже забирає інший воркер. Одночасно задача має одного власника.
  5. Python-воркер → дочірній процес. Реальне обчислення simulated annealing виконується в окремому Python-процесі; основний процес залишається доступним для heartbeat, скасування й тайм-ауту.
  6. Воркер → PostgreSQL → API → браузер. Прогрес і результат потрапляють у БД. API читає стан кожні 750 мс і передає зміни через SSE.
  7. Autoscaler → settings → Supervisor. Розмір черги визначає ціль від 2 до 4 воркерів. У локальному запуску Supervisor створює додаткові процеси. Перед зупинкою резервного процесу очікує завершення його задачі.

Атомарне отримання задачі

UPDATE jobs AS job
SET status = 'running', worker_id = $1, attempts = attempts + 1
FROM (
  SELECT id FROM jobs
  WHERE status = 'queued' AND cancel_requested = false
  ORDER BY created_at, id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
) AS next
WHERE job.id = next.id
RETURNING job.*;

Статус і власник змінюються в одному SQL-запиті. Оновлення результату перевіряє worker_id, статус і номер спроби: застарілий воркер не може перезаписати новішу спробу.

Модель розрахунку

Кожна задача має тривалість, дедлайн, залежності й допустимих виконавців. Один виконавець не робить дві задачі водночас. Залежна задача починається після завершення всіх попередників.

Спочатку будується допустимий жадібний розклад. Далі simulated annealing змінює порядок і призначення ресурсів, зберігаючи найкращий знайдений варіант. Ціль: загальна тривалість + 2 × сумарне запізнення. Це евристичний пошук: глобальний оптимум не гарантується, але результат не гірший за початковий за цільовою оцінкою.

Межі та відмовостійкість

Типово: 80 задач у розкладі, 8 виконавців, 2 млн ітерацій, 6 активних розрахунків на користувача, 120 секунд виконання. При тайм-ауті дочірній процес обчислення примусово зупиняється. Після втрати heartbeat воркера задача повертається до черги; не більше трьох спроб.

База даних залишається єдиною точкою збереження стану. У локальному запуску всі процеси працюють на одному комп’ютері. Docker-конфігурація має окремі контейнери API та воркерів; автоматичне створення нових Docker-контейнерів у цьому режимі не реалізоване.
